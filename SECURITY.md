# Security

Ennyn runs inside other projects: in their commits (the commit-msg hook) and in their Claude Code sessions (the plugin's hooks). A defect in it can be a defect in each of them.

## Reporting a vulnerability

Report it privately, through GitHub's private vulnerability reporting (the repository's **Security** tab, **Report a vulnerability**). Do not open a public issue for it. Say which version (`package.json`) or commit, which command or hook, and the smallest input that shows it.

## Supported versions

Fixes land on `main` and go out in the next release. Only the newest release is supported: an older version gets no fix.

## Where to get it

Ennyn comes from one place, `github.com/boranb/ennyn`: through its Claude Code marketplace, or as a clone. An update takes what the repository's default branch holds at that moment, and a commit-msg hook installed from the plugin runs the updated code from the next session on. A genuine copy holds no binaries, no runtime dependency and no install script (`package.json`). A copy that ships an executable, or asks you to run one to set it up, is not Ennyn; report where you found it.

## Platforms

Linux and macOS, and Windows through WSL: the test suite passes on Ubuntu 22.04 with git 2.34.1, the oldest git supported; in WSL its whole run last passed on 2026-11-09, at commit `c5d7b70`. On native Windows the test suite does not pass (its fixtures need a POSIX machine: `/bin/sh`, links, FIFOs, modes). Measured there instead, by hand (cycle 23, 2026-11-05, at commit `41cfa37`: Windows 10, Git for Windows 2.47.1, Git Bash, PowerShell 7.4.22 and Windows PowerShell 5.1, Node 22, Claude Code 2.1.317), and holding as this file says:

- the push hook, fed the input of the `Bash`, `PowerShell` and `Monitor` tools, the project's folder spelled `C:\`, `c:\`, `C:/` or with an 8.3 name; a deny stopped a live call of the `Bash` and the `PowerShell` tool (the installed plugin, an older version of the reader: this shows the deny, not this reader);
- the commit-msg hook, committing from Git Bash, PowerShell and `cmd`: a typed message, an untyped one, CRLF line ends, and a message file with a byte order mark or in UTF-16. With `commitMsg.types` set, a byte order mark is refused and said; with none, the message passes with the mark kept in the subject. A UTF-16 message is refused by the hook, saying so, where `commitMsg.types` is set, and by git itself (its NUL bytes), after the hook, where none is;
- the gate-loosening check through that hook from each of the three shells; a CRLF config and one headed by a byte order mark from Git Bash only;
- the plugin's version record, its data folder given as `C:\`, `c:\`, `C:/` or an 8.3 name by `--plugin-data`, and as `C:\`, `C:/` or an 8.3 name by the session's variables; with the folder renamed or moved after install the hook lets commits through and says it is not checking them.

The compaction hook was run only on a test project (it held an idle compaction while a task was mid-way, three runs), not in a session; its limit of 2 seconds per git call was near there (one call took 1.3). The side-copy and conversation-style hooks were not measured natively.

## What Ennyn runs on a machine

- **The commit-msg hook** (`ennyn install-hook`, never installed without being asked): `node scripts/ennyn.mjs commit-check` on every commit. Installed from the plugin, it runs the CLI of the plugin version recorded in the plugin's data directory (`${CLAUDE_PLUGIN_DATA}/root`, one line naming the version the latest session ran); with no record it lets the commit through, saying so; anything else it cannot run (a link or no regular file in the record's place, a line that is no absolute path or holds a control character, a version that is gone) refuses the commit rather than pass it unchecked or run a path the repository could name. install-hook refuses a data directory inside the repository. Under a tracked `core.hooksPath` or husky it writes nothing and prints a block the project pastes at the top of its own hook, which names no path of any machine and runs at the work tree's top: it drops every empty, relative or in-tree entry from PATH (filtered, not refused), runs node with no `NODE_OPTIONS` or `NODE_PATH`, finds the data directory as `ENNYN_PLUGIN_DATA`, `CLAUDE_CONFIG_DIR` or `HOME` names it, and then does what the hook does with the record. It refuses the commit when none gives an absolute path, when the data directory or the record's CLI lies inside the work tree, and when that CLI is a link, so what a repository holds does not choose what runs (the rest of that hook is the project's own code). The hook Ennyn writes runs the first `node` on PATH, whatever directory holds it (`hook-node-in-repo`). The block's limits: what sets a shell's startup from the environment (`SHELLOPTS=noexec`, `BASH_ENV`, `ZDOTDIR`, `BASH_FUNC_*`) or `UNAME_s` changes what the hook's shell runs, and whoever sets those has the power of `--no-verify`, with no flag to see; so has whoever points `ENNYN_PLUGIN_DATA` or `CLAUDE_CONFIG_DIR` at a directory outside the work tree, whose record names what runs; husky's generated stub is not read, only whether the index holds anything in its directory; a version manager's shim kept on PATH can pick its node from a repository file (from memory, not measured); a work tree that holds the data directory (the dotfiles pattern) refuses clean commits, and install-hook answers `dataInRepository` there; a project whose only node lies in the work tree commits unchecked, and doctor says so; a NUL or a C1 byte in the record is read as each shell reads it; `~/.config/husky/init.sh` exiting, `HUSKY=0` and `--no-verify` skip the hook; a project line after the block can rewrite the message, and what is committed goes unchecked. `doctor` counts a hook as checking only when it holds what install-hook printed, byte for byte and first; it reads no hand-written shell, so any other text that names commit-check warns and stops no commit. The line, unlike the block, runs the first `node` on PATH, so it does not count under husky, whose runner puts `node_modules/.bin` first, or in a tracked hook naming a path in the work tree. Where it does count, and for the hook Ennyn writes, an in-tree `node` first on PATH, by a relative or an absolute entry, runs instead of the real one and the secret check does not run, while doctor shows ✓ (`hook-node-in-repo`). It reads the message, the git config that shapes it, the config as the commit holds it (the index, and HEAD's to compare: the work tree's is read only to say that it differs, or when git cannot answer or no commit holds a config), the staged paths, the lines the `review.forbidden` rules name, and both versions of the staged CI files, lock files and `.npmrc`, and of each `package.json` a lock read names (beside it, and in each workspace or linked folder; its dependencies and overrides only) (of an `.npmrc`, only the keys that change where npm fetches packages from, which config it reads, or what it runs: `registry`, `<scope>:registry`, `scope`, `replace-registry-host`, `proxy`, `https-proxy`, `http-proxy`, `strict-ssl`, `ca`, `cafile`, `userconfig`, `globalconfig`, `prefix`, `cache` with `offline` or `prefer-offline`, `script-shell`, `node-options`, `git`, `shell`, `ignore-scripts`; tokens and other values are not shown). For the secret scan (`security.secrets`) it also reads, from git, the lines every staged file adds (the files a commit adds whole, by their object; the smallest first, up to 64 MB of a commit), the names the commit adds, and a file whose added lines look like part of a private key, whole; it prints where a secret is and its kind, never the secret, and the scan connects to nothing. For private text (`security.privateText`) it reads, when a rule on text is on, the lines every staged file adds, the names the commit adds and the message as git will store it, HEAD's version of a file where a line hits (a line HEAD holds was moved, not written), the list of private words in the state dir (SHA-256 digests, never the words: `ennyn private-text add` takes them on stdin; a clone with none checks no listed word, said on every commit when `security.privateText.listExpected` is on, never refused), and, with `provenance`, the staged and HEAD graph; it prints the place, the rule and a length, never the text it matched (a name is shown with that part cut; a graph that does not parse is named with a line and column, never the parser's excerpt), and connects to nothing. A digest of a short word is reversed by trying a list of names, which is why the list stays in the state dir and out of the repository; whoever can read `.git/` can try. It writes nothing. It connects only when a commit changes a lock file (below). Every git call it makes has a time limit (60 s; a streamed read, 60 s with no output): a git stopped there, or a file git cannot diff, is read whole by its objects for the secret scan (a staged entry whose object is no blob refuses the commit, by name, or, when git cannot give the types, as the read it stops; a git that fails or is killed there is said) and left unread, said, by `review.forbidden`, and the rest is still checked; each slow file costs one limit, so two of them (120 s) reach the 2-minute default of Claude Code's Bash tool, which then ends the commit instead of passing it. A size is the same kind of ceiling: a file whose diff passes git's 64 MB buffer is left unread, said, by `review.forbidden`, the secret scan reads 64 MB of a commit and says the files past it, and the rest is still checked. A stopped git counts as a fault of the machine, so a file built to make git's diff outlast the limit would take itself out of `review.forbidden` at exit 0, said, with the secret scan still reading it whole; no such file is known, and a review tried to make one.
- **Claude Code hooks** (`hooks/hooks.json`): after a file tool touches a side copy of the project, the project's path-scoped rules (`.claude/rules/`) go into the session, and the list of rules given is kept in the state dir (`paths.stateDir`); at session start, that list is reset after compaction, the conversation style text (`styles/`) is given, after a compaction a fixed line in the project's language asks to re-read the task's changed files and impact table (it names no file, and `compaction.defer: false` turns it off), and the version the session runs is recorded in the plugin's data directory (it replaces only its own record, never a version Claude Code has marked replaced), and a line naming that directory and that version (`ENNYN_PLUGIN_DATA`, `ENNYN_PLUGIN_ROOT`, shell-quoted, added once) is added to the file Claude Code runs before the session's Bash commands (`$CLAUDE_ENV_FILE`). The re-read line asks the agent to run `git status` and `git diff` in its worktree: like any git call there, they run what that worktree's `.git` config names (`core.fsmonitor`, hooks such as `post-index-change`), which Ennyn's own hooks avoid in their git calls. Before a compaction, the PreCompact hook reads the last 4 MiB of the session's transcript and the times of its subagents' files, and asks git for names and times in the session's folder (`rev-parse`, `log`, `diff-index --cached`, `ls-files`). It runs no `git status` and no tracked file's content goes through a filter (git reads `.gitignore`), so no filter, no file-system monitor and no promisor fetch runs. From git 2.38 a bare-looking folder a clone brought in is refused; a lower git, the floor 2.34.1 too, reads it as a repository, so the hook refuses it itself: every such folder is found by walking up from the session, so a session inside its own git dir, whatever that folder's `commondir` file names, gives no names and writes no log, on any git. A tree git names that is not the session's (`core.worktree`, or a `.git` file naming another repository's main `.git`) gives no names and no log. What stays open needs the `.git` entry itself, which no commit can hold: whatever can write that entry can make another repository read as this session's own (a `.git` file naming a linked worktree's dir, a separate git dir or a folder with a `commondir` file, a `.git` dir whose `index` is a link, a `.git` link to a store of another name), and the hook then gives that repository's names, and for a session started there it can write its log in that repository's git dir. It keeps nothing of the transcript: its log (`compact-boundary.jsonl` in the state dir, at most 256 KiB) holds numbers and reasons, no names and no text but the kind of a transcript line that made it pass, a short plain word. What it prints goes to the model as part of the summary's instructions: a fixed request, in the project's language, and at most 20 file names from git, each one JSON string of printable ASCII (every other character, and `<` and `>`, escaped) and cut to 120 characters, and how many were left out. A file name can still say anything in its 120 characters; it reaches the model marked as a name. `compaction.defer: false` turns the hook off: past the one `git rev-parse` that finds the config, as in every hook, it calls no git, reads no transcript, writes no log and prints nothing.
- **What the push and kill hooks guard against: habit, not intent.** They stop a command an agent writes by habit or carelessness, the shapes agents write: in one machine's transcripts, 389 kill commands from five projects other than Ennyn were `pkill -f` (154), a literal PID, `kill $PID`, `kill $(cat a.pid)` and `lsof -ti :3000 | xargs kill`, and none held a shape written to get past a reader (`$'\x70kill'`, `hash -p`, `BASH_ENV`, `${x:-pkill}`, `set -- pkill`, a kill word through `eval`, `alias` or a helper's `"$@"`). An agent that means to get past them, its own aim or text injected into what it reads, is the other case: such text can as easily say `python -c` or write a script, which no reader of a command's text reaches. Against it stand the permission mode, the ask rules, Claude Code's sandbox where it is on, and an operating-system boundary (a sandbox, a container, another user). So a shape only such an agent writes is a stated limit of the hooks, not a defect to patch, and the cycle's reviewers judge the hooks this way (`skills/cycle/finding-schema.md`).
- **The push hook is a backstop, no boundary** (`hooks/hooks.json`, PreToolUse on `Bash`, `Monitor` and `PowerShell`, in a project with an Ennyn config): it reads a shell command's text, runs none of it, and refuses every push but a plain `git push` with literal words at the head of a top-level command, in a text under 9,000 characters that holds nothing but plain words, space, newline, `;`, `|`, `>`, `&&` and `2>&1`, in every permission mode, `bypassPermissions` included (Claude Code 2.1.310, `test/reference/pretooluse.json`). What stands in front of a push is the cycle's question, the ask rule and, under `push.mode` `ask`, the hook's own ask of each plain push it leaves; under `push.mode` `after-closing` a bare `git push` the decision allows runs unasked where no ask rule stands, at any time, since the hook then stays silent and the cycle asks nothing (`skills/cycle/push.md`). This stops a push written another way by habit. It is no boundary: hand-crafted shapes pass and always will, and a program set on pushing gets through. It does not reach a script the agent writes and runs, an interpreter, another program that runs text it is given, an MCP tool, `gh api`, a command a container or another machine runs, sent by a program other than ssh (`docker exec`, `vagrant ssh -c`), what an ssh config file runs (`RemoteCommand`), text fed to a group, a function or a shell later in the session, a command held whole in a variable or a head and a verb in two, encoded words (`$'g\x69t'`), a word a run puts together, a link or copy of git under another name, a shell's name table, a program that calls git, a program that runs another and no list of the reader holds (`conhost`, `wt`, `winpty`), a WSL launcher whose name no pattern holds (`Manjaro.exe`), an alias in a config file or one whose name holds a space, or a git option or setting that runs a command (`--upload-pack`, `--exec`, `-x`). It also does not reach text whose shell grammar it does not read, so it sees no push at all: the line that leaves a push is consulted only for a push the reader sees. Claude Code's own checks hold two such texts today, which is no promise, and `test/reference/pretooluse.json` rereads them: `echo ${x:-{}; # }; git push origin main` and `echo <1-2># | git push origin main`. Claude Code's 50 ms parser deadline on a loaded machine is unmeasured, for a left text as for any other. A Skill's shell block fires no hook. Project settings can turn hooks off (`disableAllHooks`) or run the repository's code in the hook's place (`NODE_OPTIONS` or `PATH` in `env`). A config an earlier call moved away ends the hook. A hook that crashes, is killed or times out does not stop the call: Claude Code runs it. So does input the hook cannot read, which it says to the user and not to the model. PowerShell commands go through the same reader as shell text, and PowerShell's own spellings are not read: `iex`, its backtick escape, a Windows path written unquoted (`C:\PROGRA~1\Git\cmd\git.exe push`). Nor is a call on an expression (`& (Get-Command git).Source push`). On Windows 10 the hook refused on the Bash and the PowerShell tool of Claude Code 2.1.317, and these are read (measured with pwsh 7.4.22, Windows PowerShell 5.1, Git for Windows 2.47.1 and WSL): git by its Windows path in quotes or a `.cmd` shim, a batch file named like a builtin (`./test.bat git push`), a shell named with `.exe` or `powershell`, the text `wsl` with no `--exec`, a WSL launcher's `run` or `-c` (`ubuntu.exe run`), `runuser` and util-linux `script -c` give to a shell, `Start-Process git "push …"` and its aliases `start` and `saps`, cmd's caret (`cmd /c git pu^sh`), a program named like one that only reads but by its folder (`./echo.exe git push`: a work tree can bring one that runs its words), and PowerShell's splat at git's verb place (`function g { git @args }; g push`). A text that may define a shell alias, by holding the word `alias`, `sal` or `nal` anywhere but in git's `alias.x` key (bash's `alias` however called, `builtin`, `command` or `eval` before it; PowerShell's `Set-Alias`, `New-Alias`, `Set-Item alias:g`, `New-Item -Path alias:g`, `${alias:g} = …`, colon parameters), refuses every command with a push word whose program is not git by its own name, whatever the alias is: each way of defining one, read one by one, missed another (cycle 23). The cost: a push word that is no push under an alias is refused too (`g stash push`, `g log --grep push`, `g commit -m 'push later'`, `alias ll='ls -la'; ll push`). An alias the session's shell already holds, from the user's start-up files that Claude Code's shell snapshot brings (`.bashrc`, an oh-my-zsh `gp`), is in no text and is not read: unmeasured. A word reads one way, as the shell passes it, where no second shell reads it again: `git -C "C:\x" commit -m "… push …"` and `"g\it" push` run directly are no pushes and are left. Where one does, its reading is made: what `wsl`, a launcher or a shell is given refuses on any push word, and ssh's command words are joined with one space and read as the other machine's shell reads them (`ssh host "true;git" push`, `ssh host git "\-C" dir push`), past ssh's options as OpenSSH 8.9p1, 9.5p1 and 9.9p1 take them; a push word in ssh's own words (`-o ProxyCommand=…`, which runs here) and a push in what an ssh with no command is fed refuse too. Whether the `PowerShell(git push *)` ask rule reads a compound is unmeasured.
- **The kill hook is a backstop, no boundary** (`hooks/hooks.json`, beside the push hook, PreToolUse on `Bash`, `Monitor` and `PowerShell`, in a project with an Ennyn config): it reads a shell command's text, runs none of it, and refuses a kill chosen by a filter, a name, a window title, a port or a PID looked up at run time, in every permission mode: `pkill`, `killall`, `taskkill` with `/FI` or `/IM` (`//FI`, `//IM` as Git Bash writes them, any case) or with no `/PID`, `Stop-Process -Name` and a `Stop-Process` fed by a pipe, `kill` of a substitution or of a variable this text did not set from `$!`, a kill program after `xargs`, `fuser -k`, `kill-port`, `wmic process … delete`, and PID 0 or -1; a shell's text (`bash -c`, `eval`, `powershell -Command`, ssh's command) is read again, a word with `$` or a backtick in it too. Where the text can turn a word into a program (a function it defines, `eval`, `trap`, `source` or `.`, `set`, `xargs`, `alias`, `declare`, an exported function, an expansion at a program's place, shell text past four levels), a kill word anywhere in it, in any quoting and inside a word (`pkill${IFS}node`), refuses it unless it is a kill the reader judged and passed: `retry() { "$@"; }; retry pkill node`, `bash -c "$(echo pkill) node"`, `set -- pkill node; "$@"`, `echo pkill node | xargs env`; the refusal names the kill word and the construct, so the command can be split. It refuses some commands that kill nothing (`set -e; grep kill src`): 92 of 89,300 in one machine's transcripts. A program name a run joins to letters (`$(echo pk)ill`) is refused. A kill by a literal PID or process group passes (`kill 1234`, `kill -- -1234`, `taskkill /PID 1234 /T /F`, `Stop-Process -Id 1234`), and so do `kill $pid` after `pid=$!`, a PID file the agent wrote read whole (`kill $(cat app.pid)`, `P=$(cat app.pid)`, PowerShell's `Get-Content`), a loop over literal PIDs and `Stop-Process -Id $p.Id` after `$p = Start-Process …` in the same call, and `kill $(jobs -p)`. It stops a kill written by habit, as a reviewer once wrote `taskkill //F //FI "WINDOWTITLE eq *"`, which matches every window on the desktop. A PID file's name is resolved before it is judged (`//`, `/./`, `..`; a variable only at its start), and it is trusted only where every mention of it in the same text reads, tests or removes it or writes it, in a listed shape, from `$!` or a name it trusts: a glob, stdin (`-`, `/dev/stdin` however spelt), `/proc/` (but Git Bash's `/proc/<pid of $!>/winpid`), another tool's run folder (`/run/`, `/var/run/`), a file the text fills from `pgrep`, `netstat` or `Get-NetTCPConnection`, and one it writes any other way (`&>`, `>|`, `tee`, `cp`, `ln`, `New-Item`, `[IO.File]::WriteAllText`, `Copy-Item`) are refused, as is a name a `declare -n` binds. A PID file the agent's earlier call filled from a port lookup is refused too: the replay's refusals of the agent's own `netstat … > app.winpid` files are this rule. A PowerShell block's braces are read wherever they sit in a word (`ForEach-Object{Stop-Process`, `.{…}`, `%{`, `-Force}`), a program's name is read as the last segment of a Windows path as written (`C:\Windows\System32\cmd.exe /c …`, `$env:SystemRoot\System32\taskkill.exe`), and a `kill` or `Stop-Process` whose target is a parenthesised expression (`Stop-Process (Get-Process x)`) is refused. With a kill word in the text, a shell fed by a pipe or a here-document (`echo 'pkill x' | sh`, `bash <<X`, `pk\ill` among them) or given its whole text by a run (`sh <(…)`, `source <(…)`, `bash -c "$(…)"`) and a program's name built by a run, at a head, in a function body or after a wrapper (`"$(echo pkill)" x`, `env $(echo pkill) x`, PowerShell's backtick) are refused unread, as is an encoded command in any spelling PowerShell takes (`-enc`, `/ec`, `--EncodedCommand` …) after `powershell` or `pwsh` anywhere in the text, whatever it holds; a kill method named as a string (`.ForEach('Kill')`, `.Methods['Kill'].Invoke()`) is refused. It does not reach a script the agent writes and then runs, an interpreter (`python -c`, `node -e`), an alias or a function defined earlier (`Set-Alias`, a function, a `$cmd` variable at a command's head), a command held in a variable, text that becomes a program only when it runs (`$'\x70kill'`, `printf '\x70kill' | sh`, base64 decoded at run time, `rev | bash`, `$a$b` joined in fed text, a string joined or formatted for `iex`), PowerShell's grammar past what is listed (string expansion `"$(…)"` as an argument, splatting `@args`, `&` on a variable, `Invoke-Command -ComputerName`, `Start-Job`), cmd's caret and PowerShell's backtick outside a shell's text or a program's name, a substitution in an unquoted here-document's body, a program that kills and no list of the reader holds, an MCP tool, or a PID read in an earlier call and written here as a number, or a PID file gone stale, its number given to another process, or a file of the same name another session wrote: whose process a number is, the text cannot say. Input it cannot read leaves the call and says so to the user; a hook that crashes or times out does not stop the call (`test/reference/pretooluse.json`). It judges kill programs (`kill`, `pkill`, `killall`, `taskkill`, `Stop-Process` and the others its tables list) and no other way to stop a process: `docker stop`, `docker kill`, `docker rm -f`, `tmux kill-server`, `pm2 kill`, `launchctl` and `osascript` are not read. A PID file is trusted by its shape, not by who wrote it. The rule in the task brief and the three reviewer agents is the stricter one: stop only a process you started, by its PID or process group.
- **An ask rule reads a compound command only if Claude Code's parser finishes**, and this holds for every ask rule, not only push (Claude Code 2.1.310; measured on `git push` and `npm publish`). When the parser gives up, on length, nodes, a deadline, a stack, a budget spent over the text or a here-document case, only a match on the whole text is left, so a command later in the text runs unasked in `bypassPermissions`. It takes no hostile text: `npm test > out.log 2>&1 # it's slow` and a command on the next line is enough, since after a redirect a comment holding an apostrophe ends what the rule reads, with the parser finished. So is a commit message's line that starts with the here-document's delimiter and holds `)`, `}` or a backtick, and `$(` nested 14 deep. `test/reference/pretooluse.json` rereads this on each Claude Code version. The push hook keeps a push inside what the parser finishes; nothing does that for `npm publish` or the other ask rules.
- **The agent's secret setup is reported, not enforced.** `ennyn doctor` and `init-scan` say what the settings files hold: whether bypassPermissions is turned off and the sandbox on and required, the Read deny rules for `.env*`, `~/.ssh` and `~/.aws`, tokens set in the environment that sandboxed commands can still read, a `mask` credentials entry in a project file (Claude Code does not apply it), `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` (set in the environment, it starts Claude Code in the default permission mode, over bypass and `acceptEdits`: Claude Code 2.1.310), the Claude Code folder inside a git work tree that does not ignore its transcripts, and a literal secret in `.mcp.json` (its line and kind, never the value). They read the project's settings files and the user's, not managed settings or the flags a session starts with, so the mode they name is what the files ask for, not proof: Claude Code skips a settings file whole for a wrong value of any of its keys and Ennyn checks only the keys it reads, and a session started in a subdirectory reads that directory's `.claude/`. A file not read whole, or one that leads out of the repository, leaves the mode unclaimed. `/ennyn:init` writes the no-bypass block only on the user's yes, with values Claude Code 2.1.310 and 2.1.319 keep the file with; a value of one of the keys read that is not a kind measured kept (`disableBypassPermissionsMode: true`, `sandbox.enabled: "true"`, a credentials entry with no mode) may make Claude Code skip the whole file, ask rules included, and doctor says so and does not count them. Whoever keeps bypass keeps it: the lines are warnings. The sandbox covers shell commands only; Read and Edit follow permission rules.
- **Installing the plugin**: Claude Code copies the plugin into its cache and, in the version measured (2.1.207), runs `npm ci --ignore-scripts` in the plugin's root when it holds `package.json` and a lock; the documentation of later versions describes that install elsewhere. Ennyn's plugin root is the repository's, so an install fetches the two development dependencies below from `registry.npmjs.org`, and runs none of their scripts (the flag, and `.npmrc`'s `ignore-scripts=true`).
- **Removing it**: `uninstall-hook` deletes only a file install-hook recorded writing (the commit-msg hook in the hooks directory git runs, inside the git dir with no link on the way) and only while it still holds the recorded bytes: the file is moved aside, hashed there, and deleted or put back. It then deletes the state dir when it lies under the git dir with no link on its way and no mutation run left a file changed. What init's agent wrote (the config, the work graph, the handoff, the ask rules) is listed, never deleted. `claude plugin uninstall` deletes the plugin's data folder, the version record with it. The README's Remove section gives the order.
- **Commands** run only when you run them. `mutate` runs the test command it is given and edits files in place, writing each back byte for byte. `impact` runs the program `impact.referenceCommand` names, when the config sets one; `core`, `doctor`, `mechanization` and `status` (when the journal has a release set and no `--line`) import the work graph when `paths.graph` names a JavaScript module (`.mjs`, `.js`), which runs that module; no hook and no commit gate does. A config the project commits names both, so review a change to these keys as you would a package script. `test fast` and `test whole` run the commands `commands.fastTest` and `commands.wholeTest` name, and record each run in the state dir, where any process that can write the git dir can add a line: `push-check` reads a green line as the caller's word, as it reads `--tested`, and no line turns `push.mode` `ask` into a push. The cycle skill runs the command `commands.fastTest` names and those the handoff (`paths.handoff`) names: the fast test, lint, typecheck and the mutation tool; review a change to either the same way. Every git call Ennyn makes refuses, from git 2.38, a bare-looking folder a clone brought in, so a command started inside one stops on git's words and its config starts nothing. That holds on the gits measured, 2.39.5, 2.50 and 2.56. A lower git, the floor 2.34.1 too, ignores that setting and reads the folder as a repository: every call also sets `core.fsmonitor` empty, and the folder's other settings stay open there. On 2.34.1 three commands still run a program that folder's config names: `doctor`, through a `filter.<name>.clean` or `.process` on a file tracked directly under `.claude/worktrees/`, and, with `extensions.partialClone` set and HEAD's commit or tree missing, through the fetch its `git status -- .claude/worktrees/` starts, with no file there; `rework`, through `extensions.partialClone` with a blob, a tree or a commit missing; and `init-scan`, whose `git log --raw` fetches a missing commit or tree. Each fetch runs `core.sshCommand` or `remote.<name>.uploadpack` (measured, cycle 20; ten other commands ran nothing). `push-check`, added later, fetches by design, and so runs those settings of the repository it stands in; in such a folder on 2.34.1 that is unmeasured. `leftovers` runs `git status`, which runs a clean filter, so it refuses a work tree that lies in its own git dir, the shape such a folder takes to have one; a `.git` file written by hand that names such a folder, which no commit can bring, is not refused. Use git 2.38 or newer in a clone you do not trust. `worktrees --remove` deletes a worktree's folder only when its mark is a lock reason of `ennyn:<cycle>` and its folder holds HEAD's tree byte for byte, or, for a file checkout converts, the bytes checkout writes (no `git status`, whose answer the repository's stat settings move). For such a file the check runs `git cat-file --filters`, and so the repository's smudge filter for that path, as checkout does: the program a checkout of that worktree already ran. Git does not delete the folder, since Git for Windows 2.47.1 deletes through a junction in it, with or without `--force`: the folder is moved aside in one rename (a rename that fails, as on Windows while a process holds something in it, keeps it), walked again with lstat alone, which must find it and its git folder as the check saw them, and deleted with Node's `rmSync`, which unlinks a link or a junction and never enters it; only then is it unlocked, and git drops the entry of a folder no longer there. Limits stay. A file a process still running in that worktree writes after that last look goes with it (a link it makes is unlinked); a folder swapped for a junction between `rmSync`'s look at it and its reading of it would be entered, and so would a volume mount point in the worktree, which libuv does not report as a link; an NTFS alternate data stream on a tracked file or folder is not seen and goes with it. Give `--remove` a worktree whose task has stopped. And the mark is all that makes a worktree the cycle's: a mark copied by hand onto another worktree lets the command remove it when it would lose nothing.
- **No runtime dependency**: `package.json` has none. Its two development dependencies (`typescript`, `@types/node`) serve the type check only.
- **Network, only where named**: the commit-msg hook connects only when a commit changes a lock file (`security.deps.paths`), and only to the origins in `security.deps.registries`, about the entries the commit adds whose `resolved` is that registry's own tarball, or that have none and whose registry the `.npmrc` beside the lock names and `security.deps.registries` lists (with no such `.npmrc`, where that `.npmrc` leaves `scope` or a scope's registry to a user's config, or in a version 1 lock, the entry is refused and nothing is asked), and at most 160 MB an answer and 256 MB at once: by default `registry.npmjs.org` for the package document and `api.npmjs.org` for last week's downloads. `security.deps.online: false` stops it. `ennyn deps` sends the name and version of each lock entry from the public registries in `security.deps.advisoryRegistries` (by default only `registry.npmjs.org`) to OSV (`security.deps.advisories`, by default `api.osv.dev`); a private registry's package names never leave the machine, and neither do bundled packages, whose versions the lock cannot prove. `push-check` fetches the branch's upstream remote, as `git fetch` does, so the repository's own transport and fetch settings run (`core.sshCommand`, `remote.<name>.uploadpack`, a `reference-transaction` hook). `clone-setup`, with `commits.signed` set and a GitHub login, asks `api.github.com` for that login's public SSH signing keys (`GET /users/<login>/ssh_signing_keys`, no token sent), or a loopback origin `ENNYN_GITHUB_API` names, and nothing else. No other command or hook connects anywhere, but in a partial clone (`git clone --filter`) git itself fetches an object it does not hold from the promisor remote when asked for one, as any git command there does: `rework`, `impact` and `init-scan` let it. The commit-msg hook does not: every git call it makes runs with `GIT_NO_LAZY_FETCH=1` (the staged changes, HEAD's config, the `amend!` target's paths), so a staged file whose new object is not on the machine is said unread, one whose HEAD object is missing is read whole as a file the commit adds, and nothing connects; git reads that variable from 2.45 and in the maintenance releases of May 2024 (2.39.4, 2.40.2, 2.41.1, 2.42.2, 2.43.4, 2.44.1), as do distribution builds that took that fix (the Linux run's Ubuntu 22.04 git 2.34.1 and Debian 12 git 2.39.5 read it); a git without it, 2.44.0 among them, fetches the object.

## How this repository is kept

- Every action in `.github/workflows/` is named by its full commit SHA; the workflow token can only read, checkout leaves no credential behind, and `npm ci` runs no install script. The commit-msg hook refuses a new action named by a tag and a workflow that drops its permissions (`security.ci`), but `git revert`, `cherry-pick` and `rebase` run no commit-msg hook; `test/engines.test.mjs` holds the workflow's whole text.
- `npm run test:linux` runs the suite before a release on images pulled by digest.
- A commit that widens or switches off a gate is refused unless its message holds a `User-Approved-Loosening:` line naming each key: loosening a gate is the user's call. This is a tripwire and a record, not a boundary. `push.mode` takes the same line: an agent that writes it itself turns `after-closing` on, and its next bare `git push` runs unasked where no ask rule stands, two calls that lift the push hook's own ask, before the closing's list (`push-mode-self-approval`). The line approves a push, not a url: the check wants the upstream remote to hold one url that nothing rewrites, and compares it with no approved url, so a remote an earlier command changed (`git remote set-url`, or another remote set as the branch's upstream) is not seen. A local hook cannot tell the user from an agent, and `--no-verify`, `core.hooksPath`, a rebase, a cherry-pick and a revert skip it (`no-verify-gap`). So the closing report lists, for the user before the push, each commit-shape bypass with its reason and each key the range loosened with its approval line (`ennyn bypass --from <start>`), read from the configs and not from the lines. A config no commit holds (untracked, or outside the repository under `ENNYN_CONFIG`) cannot be compared: the hook says so on every commit, and the report names it unmeasured and exits 1. With a config tracked at the default place, `ENNYN_CONFIG` is said and left out of the commit's checks and of the report; every other command still reads it. A commit from anywhere but the top of the repository git is committing in is refused before any gate: a work tree apart from the git dir, a decoy repository, and a bare repository with a separate work tree.
- Stated limits of that guard. A moved config with `ENNYN_CONFIG` unset runs the defaults, silently: nothing in the commit names the path (`moved-config-unnamed`), and under a name no git argument can hold, the rename that deletes it compares with the defaults alone, said. In a project with no config at the default place, the variable decides what is read, any tracked file included, and a commit cannot show it; a project with a config at `.ennyn/config.json` is not exposed, the variable is left out there, and a commit that takes the config from that place counts whole, even with its content unchanged. An index changed after git built the tree, by `GIT_EDITOR` or `prepare-commit-msg`, is out of a commit-msg hook's sight, and `ennyn bypass` lists the commit as unapproved (`index-after-tree`); a `.git/config` spoiled in the same window makes the hook's own git fail, so no gate runs and the hook says so in one line, and with the file repaired the report lists the commit the same way. A clean filter on the config that leaves both versions unreadable lets the commit through, and the hook says so (`config-clean-filter`). A `.git/shallow` written by hand can make an ancestor named in `MERGE_HEAD` read as a new parent; git records it, and the report lists the merge (`forged-shallow-ancestry`).
- `.npmrc` sets `ignore-scripts=true`: `npm ci` and `npm install` here run no dependency's install script, while `npm test` and `npm run` still run the named script. A commit that deletes that file, drops the line or leaves npm reading an older one is said, as a value that turns install scripts on is (`false`, `null`, `undefined`, an empty list `'[]'`, a number that is zero, each with any white space around it; `no` and `off` read as true), and as a value read from the environment is, which the file does not hold. `test/plugin.test.mjs` holds that one line as npm reads it, dev dependencies at exact versions and no other dependency section, an allow list of scripts, the reviewers' tools, no shell form Claude Code runs when it loads a skill, a command, an agent or an output style, nothing but a name and a description in the front matter of a skill, a command or an output style, and an icon of drawing markup alone, its elements and attributes each on a list. The commit-msg hook refuses a new package with an install script unless `security.deps.allowScripts` names it, and install scripts the registry's manifest shows that the lock leaves out; a binding.gyp neither shows is not seen, since the tarball is not read. `ignore-scripts` does not reach a git dependency: npm builds one by running its `prepare`, so the hook refuses a new git dependency unless `security.deps.sources` names it pinned to a full commit, and any entry whose source has no one meaning it can prove: a tarball on a listed registry's host anywhere but right after a listed URL in npm's layout (another repository of the host, GitHub Packages' `/download/…`, GitLab's project registry `…/@g/n/-/@g/n-1.2.2.tgz`, another spelling) unless `security.deps.sources` names that exact `resolved`. A lock or `.npmrc` the commit brings that npm reads and the hook cannot (not UTF-8 text, a symbolic link, past 16 MB) is refused; one HEAD already holds and the commit leaves as it is is said. Not judged: a lock or `.npmrc` HEAD holds as a symbolic link whose target the commit changes, since npm reads the new target and the hook does not (work graph `deps-held-link-target-unread`).
