# The closing's push

`push.mode` in the config decides who says yes to the push at the end of a cycle. `ask` is the default; `after-closing` is the user's own choice, made at init or later in a commit that carries `User-Approved-Loosening: push.mode` (the commit-msg hook refuses one without it). The line is a tripwire, not a proof: an agent that writes it itself turns `after-closing` on, and its next bare `git push` runs unasked where no ask rule stands; `ennyn.mjs bypass` names the key only at the closing (work graph `push-mode-self-approval`).

1. `git fetch` first: the user may have pushed from another machine. A branch behind its upstream is not pushed; rebase, and the tests run on the new tree. Before the whole test command, note `git rev-parse HEAD`.
   Run the tests as `ennyn.mjs test fast` or `test whole`: each records its run by HEAD's tree when the work tree is clean. With no `commands.wholeTest` set, `test whole` runs nothing and exits 78: run the handoff's whole command instead; push-check then finds no whole run recorded, and the push is asked, or under `after-closing` goes on `--tested` (step 4).
2. Run `ennyn.mjs push-check`: it fetches, refuses a branch behind its upstream, and says what the push needs, from the commits it sends: a path `push.codeGlobs` matches needs a green whole run recorded on HEAD's tree, any other change a fast one; and it states the unpushed count and whether the cycle may push by itself. It may only when HEAD's config at the repository's top and the work tree's both say `after-closing`; the latest commit on HEAD's first-parent line that set it holds the approval line, and no commit HEAD reaches past it, on any line, set it back to ask; HEAD is on a branch; and git config sends a bare `git push` of that branch to the branch of its name on its upstream remote's one url and nothing more. That last is read by allowing: the remote holds only its url and fetch settings, `git remote get-url --push --all` gives that url back unchanged (no pushurl, second url, insteadOf or pushInsteadOf), `push.default` is simple, upstream or current, and there is no other push remote, no `push.followTags`, no submodule push (`push.recurseSubmodules`, `submodule.recurse`). Anything else: ask. Its exit has one meaning each: 0 only with the line that says the cycle may push by itself; 3 where what the push needs is met and the push is asked (`ask`, or any state above that refuses); 1 for the rest (behind, not met, unmeasured, a refused `--tested`).
3. **`ask`:** state the count and ask for push approval. Push only on the user's yes for this push.
4. **`after-closing`:** only when every closing check passed (step 5's are found, clean or fixed, none unmeasured that a check needed) and the whole test command was green, run `ennyn.mjs push-check`. It exits 0 when the record holds a green run of what the push needs on HEAD's tree and the work tree holds no change and no untracked file. Where the record holds no such run on that tree, `--tested <the hash from step 1>` stands in: HEAD must be that commit, and that the suite ran on it and passed is your word, so never pass a hash whose suite was red, skipped or cut short. A record line is a word too: any process here can write the file, and no line turns `ask` into a push. Exit 0: push with a bare `git push` (those two words, nothing after them), in a call of its own, from the repository's top, and name the push in the report (remote, branch, hash). The push hook leaves only that bare shape unasked, under the same decision, taken where the shell stands: a shell an earlier call moved into another repository, a nested one or a linked worktree asks; every other push it asks about, `--force`, a refspec, `--delete` and `--mirror` included. Any other answer: ask, as in `ask`. A red suite, a fix after the suite or a commit after it moves HEAD: the suite runs again before the push goes by itself.
5. **Report** the push under `### Push`: the mode, the count, and either the approval asked or the push made with its hash.

What this does not close: a cherry-pick of the user's own approved commit carries its line again and counts; a merge that brings the setting counts as the commit that set it and needs the line itself; a `git reset --hard` past the user's own move back to ask, before it was pushed, leaves no commit to read. A shallow clone always asks: the commit that set the mode is not there. `git commit --no-verify` skips the hook, and `ennyn.mjs bypass` lists the loosened key at the closing (section 3, step 3); push-check refuses such a commit too. Git config read in push-check's environment can differ from the push's own (another `GIT_CONFIG_*`). A `GIT_DIR` in the session's settings env is honoured by the push and not by the decision, and a transport setting (`core.sshCommand`, `GIT_SSH_COMMAND`) can send the bare push to another host with the url unchanged: both are open (work graph `push-mode-git-dir-env`, `push-mode-transport-settings`). With `after-closing` a bare `git push` also runs unasked at any other time the decision holds, since no ask rule stands for it.
