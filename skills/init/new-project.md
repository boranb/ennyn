# A new project

`init-scan` says whether the folder is a new project (`newProject`): nothing in it, in the index or in the last commits of any ref but a README, a licence, `.gitignore`, agent instruction files, Claude Code's settings and Markdown in `.claude/`, and Ennyn's data in `.ennyn/`. `found` names what is not; what could not be measured (`unmeasured.newProject`) is never new.

1. **Inside another work tree** (`within`): stop before any question. Say that this folder lies inside `within` (a work tree that tracks nothing here or, with `repository` false, a folder holding a `.git` git does not read from here), and ask whether to set up that project (scan again from its top) or to start the new one outside it. Never run `git init` here, and take none of that tree's history or files for this project's.
2. **No repository** (`gitInit`): propose `git init` in this folder. On the user's yes run it with `GIT_DIR` and `GIT_WORK_TREE` unset (with `GIT_DIR` set, git init writes there and leaves this folder as it was), then scan again; a scan that proposes it again means it did not take: stop and say so. On a no, go on: what needs history stays unmeasured. No repository and no proposal (`noGitInit`): say its reason and propose none. Not new (`found`): go on with SKILL.md as written.
3. **New** (`new`): say in one line that this is a new project, then ask only what the config and the starting graph need: SKILL.md's questions 1, 2 and 5 as they stand, 6 when `agentSetup.overlaps` lists something, and from 4 the ask rules ([gates.md](gates.md)) and whether cycles run unattended. From 3 ask only for the fast test (a test command of `commands`, else the command the project will run, or why it has no tests yet), written to `commands.fastTest` (`{ "none": "<why>" }` for none); skip the rest of 3 and of 4: their survey is empty, and every value they set keeps its default. Then go on at SKILL.md's section 3, then step 4.
4. **The first commit**, at SKILL.md's section 7, before any scaffold or install: a commit hook sees a lock file only after its install scripts ran, so only settings committed before the first install reach that moment. On the user's yes, write these, add them by name and commit them alone, in the agreed convention; the scaffold and the install come after, in commits of their own. With no repository (a no to `git init`), write `.gitignore` and `.npmrc` all the same; the commit and `install-hook` wait for a `git init`.
   - `.gitignore`, keeping its lines and adding those it lacks: `.env`, `.env.*`, `!.env.example`, `.netrc`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*`, `id_ecdsa*`, `.claude/settings.local.json`, `node_modules/`, `dist/`, `build/`, `coverage/`, and the build folder of the stack the user names (`target/`, `__pycache__/`, `.venv/`).
   - For npm, or when no package manager is named yet, `.npmrc` with `ignore-scripts=true`: on install no dependency's scripts run, nor the project's own `prepare` and `postinstall`; `npm test` and `npm run` still run their script, without its pre and post scripts (measured, npm 10.9.9). Read `npm -v`: from 11.15.0 add `min-release-age=<days>` with the days of `security.deps.cooldownDays` (7 by default). Below 11.15.0 write none and say why: npm before 11.10.0 has no such key, and from 11.10.0 to 11.14.1 it fails an install whose git dependency has a build step, or any install when the user's config sets `before`. The commit hook's `security.deps.cooldownDays` is then the only age check.
   - npm reads `.npmrc` only in its prefix: the first folder up that holds a `package.json` or `node_modules/`. Before the first install in any folder, the root included, check there that `npm prefix` prints that folder (as `pwd -P` prints it) and that `npm config get ignore-scripts` prints `true`. A scaffold into a subfolder (`npm create vite@latest my-app`) has its own `package.json`: copy `.npmrc` there first. A prefix above the folder (a stray `package.json` or `node_modules/` there) means the install would run there, unguarded: say so, and install nothing until the user decides; write no `package.json` for them. After the scaffold, check that `.gitignore` and `.npmrc` still hold their lines: scaffolders write their own.
   - For pnpm, read in pnpm 12.16.1's changelog (its package runs a native binary, so the settings were not run): `minimumReleaseAge` in minutes (default 1440), `allowBuilds` and `strictDepBuilds`, in `pnpm-workspace.yaml`. For uv, `exclude-newer` is not measured. Name them and write them only on the user's yes.
   - `.ennyn/config.json`, the graph, the handoff, and `.claude/settings.json` with the ask rules ([gates.md](gates.md)).
   - The commit-msg hook: `ennyn install-hook --plugin-data "${CLAUDE_PLUGIN_DATA}"` before the commit, so the hook checks this commit too; it works in a repository with no commit.
